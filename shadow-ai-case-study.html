Overview

Project Overview

Shadow AI Detection explores how organizations can monitor and investigate unauthorized use of generative AI services. The system processes network telemetry collected through Zeek and applies configurable detection logic to identify AI-related activity and potential data exposure.

The project focuses on providing investigation signals rather than claiming to automatically prove malicious activity. Detection events are correlated, deduplicated and stored for analyst review through a security dashboard.

Challenge

The Problem

The rapid adoption of generative AI tools introduces a new visibility challenge for organizations. Employees may access public AI services to process code, documents or other organizational information without those services being formally approved or monitored.

Traditional network monitoring may reveal that a user communicated with an external service, but identifying AI-related activity and determining whether potentially sensitive information was transferred requires additional detection logic and contextual evidence.

Shadow AI Detection was created to explore this problem from a defensive security-monitoring perspective.

Security Relevance

Why Shadow AI Matters

Organizations face several challenges when it comes to visibility into AI usage.

AI Service Visibility

Organizations may have limited visibility into which AI platforms are being accessed from their networks.

Data Exposure Risk

Employees may unintentionally transmit sensitive information to external AI services.

API Usage

AI usage can occur through applications and APIs rather than only through browser-based websites.

Security Investigation

Security teams need evidence and context rather than simple binary alerts to investigate effectively.

Detection indicators are not automatically proof of malicious activity or confirmed data loss. They are signals intended to support investigation.

Goal

Project Objective

The objective was to build a lightweight security monitoring pipeline capable of:

Detect Configured AI Domains

Identify connections to known/configured AI services using DNS and network telemetry.

Identify AI API Activity

Detect AI-related API requests such as chat completion and embedding endpoints.

Detect Large Outbound Transfers

Flag potentially significant outbound data transfers for investigation.

Correlate & Deduplicate

Reduce alert noise by correlating related events and suppressing duplicates.

Store Detection Events

Persist detection data in SQLite for later review and investigation.

Visualize Security Events

Present detection events through a monitoring dashboard for analyst review.

Technical Deep Dive

Detection Pipeline

How the system processes network telemetry and applies detection logic.

DNS Detection

The detector evaluates DNS telemetry against a maintained list of configured/known AI-service domains.

Example: ai-service-domain.com

SSL/TLS Metadata

SSL/TLS-related telemetry provides context about encrypted connections without requiring the system to claim visibility into encrypted payload contents.

Connection Analysis

Connection telemetry provides context about network endpoints, timing and traffic volume, enabling detection of unusual patterns.

HTTP Detection

When HTTP telemetry is available, the system inspects request metadata for AI-related API indicators.

POST /v1/chat/completions POST /v1/embeddings

Data Exposure Heuristic

The detector identifies unusually large outbound transfers using a configurable threshold. During development, approximately 200 KB was used as a test threshold.

This is a heuristic and does not prove that sensitive information was transferred.

Correlation

Evidence Correlation & Deduplication

Network telemetry can generate multiple observations for related activity. The system uses evidence hashing and time-based correlation to reduce repeated detections.

Current Implementation: 5-minute correlation window

Events occurring within the configured correlation window are compared using an evidence hash to identify repeated or related observations.

Raw Events → Normalize Evidence → Generate Evidence Hash → 5-Minute Correlation Window → Deduplicate → Store Detection

Goal: Reduce Alert Noise

Treating every observation as a separate security incident can create unnecessary noise. The correlation and deduplication logic helps analysts focus on unique events rather than repeated duplicates.

Goal: preserve useful investigation evidence while reducing unnecessary duplication.

Problem Solving

Engineering Challenges

Challenge: Correlating network evidence

Related activity can appear across multiple network logs, making it difficult to connect observations.

Solution: Implemented evidence hashing and time-based correlation.

Challenge: Reducing alert noise

Repeated observations can generate duplicate detections, overwhelming analysts.

Solution: Used deduplication and correlation logic with a 5-minute window.

Challenge: Detecting more than website visits

AI usage can occur through APIs rather than only browser-based websites.

Solution: Added detection logic for supported AI API patterns.

Challenge: Turning raw logs into investigation data

Raw telemetry can be difficult to interpret directly without processing.

Solution: Built a processing pipeline that transforms relevant events into structured detection records.

Security Mindset

Security Considerations

Detection ≠ Proof

An alert indicates activity requiring investigation; it does not automatically prove malicious behavior.

False Positives

Detection rules can produce false positives and should be tuned against organizational traffic patterns.

Encrypted Traffic

The system should not claim to inspect encrypted payloads unless endpoint or other appropriate telemetry provides that visibility.

Privacy

Network monitoring should be implemented with appropriate organizational policies, access controls and privacy considerations.

Threshold Tuning

Data-transfer thresholds should be configurable rather than treated as universal indicators of compromise.

Evidence Quality

Detection systems should preserve sufficient context for analysts to validate an alert.

Reflection

Lessons Learned

Building Shadow AI Detection changed how I approach cybersecurity engineering. I learned that effective detection is not simply about writing rules that trigger alerts. The quality of telemetry, correlation, evidence and investigation context all influence whether a detection is actually useful.

Security monitoring depends on quality telemetry.

Detection rules require careful tuning.

Correlation helps reduce alert noise.

A detection is not automatically proof of compromise.

Analysts need evidence and context.

Network visibility has technical limitations.

Security tools must balance visibility, performance and privacy.

Defensive engineering requires continuous testing and refinement.
